## 三、组件分层与目录结构

pages/ 或 app/：路由入口，只负责数据获取编排和布局组装，不写业务逻辑

features/：按业务域划分（如 order/、user/），每个 feature 内含自己的 components/、hooks/、services/、types.ts

shared/：跨 feature 复用的 UI 基础组件（Button、Modal）、工具函数、通用 hooks

services/：API 调用层，所有请求集中封装，组件不直接调用 Axios

## 四、状态管理分层

React 方案最容易失控的地方是状态放错位置。方案中应给出明确的分层规则：

状态类型 存放位置 示例
组件私有 UI 状态 组件内 useState 弹窗开关、输入框临时值
兄弟组件共享 提升到最近公共父组件 筛选条件与列表刷新
跨页面/全局 Context 或 Zustand 当前用户信息、权限码
服务端数据 TanStack Query / SWR 列表数据、详情数据
原则：能放局部不放全局，服务端数据不复制到全局 store（避免缓存不一致）。如果项目已用 Redux，需注明新模块是否沿用及理由。

## 五、接口契约与数据流

与后端方案中的“接口契约”章节对齐，但前端视角需额外关注：

请求/响应类型定义：用 TypeScript interface 或 zod schema 描述，与后端 DTO 保持一致。建议直接引用后端提供的 OpenAPI 生成类型，或手工维护 types/api.ts。

数据转换层：后端返回的字段名/结构与前端 UI 模型不一致时，在 services/ 层做转换，组件只消费前端模型，不直接处理原始响应。

错误码处理策略：哪些 HTTP 状态码或业务错误码需要弹出全局提示（如 401 跳登录、500 提示“服务繁忙”），哪些由页面局部处理（如表单校验 422）。需列出错误码与处理方式的映射表。

加载与空态：每个异步数据依赖的页面需标注 loading / empty / error 三态的处理方式，避免开发时遗漏。

## 六、关键交互与状态流转

用简图或表格描述核心页面的状态变化，尤其是涉及多步骤或条件分支的流程。例如：

表单页：初始 → 校验中 → 提交中（按钮禁用）→ 成功（跳转/提示）/ 失败（定位到错误字段）

列表页：加载中 → 有数据 / 空列表 / 加载失败（重试按钮）

不需要画完整的状态机图，但提交中防重复点击、请求竞态处理、组件卸载后 setState 防护这几类问题应在方案中标注处理方式。

## 七、样式与设计系统接入

设计 token 来源：色值、字号、间距、圆角从 DESIGN.md 或 Figma token 导出，代码中禁止硬编码原始值，统一通过 CSS 变量或 Tailwind 配置引用。

组件库策略：使用 Ant Design / MUI 等现成库时，注明版本与主题定制方式（ConfigProvider / ThemeProvider）；自研基础组件时，说明与设计系统的映射关系。

响应式断点：定义项目统一的断点值，避免各页面各写各的。

## 八、性能与体验兜底

代码分割：路由级懒加载（React.lazy + Suspense），首屏不加载非必要 chunk。

列表渲染：超过一定条数（如 100 条）使用虚拟滚动，注明阈值和选用的库。

图片与静态资源：懒加载、尺寸压缩、CDN 路径约定。

错误边界：至少按路由级设置 Error Boundary，避免单个组件报错导致整页白屏，兜底 UI 需给出设计稿或描述。

网络异常兜底：接口超时（建议默认 10s）和失败重试策略，是否显示重试按钮。

## 九、测试与验收

单元测试范围：工具函数、自定义 hooks、纯展示组件的 props 渲染。

组件/集成测试：表单校验、条件渲染、用户交互（React Testing Library）。

验收标准：每个页面的关键路径写成可执行的测试用例或手动验收清单，例如“提交订单后按钮进入 disabled 状态，成功则跳转 /orders/:id，失败则保留表单数据并显示错误提示”。

## 十、与后端的联调约定

Mock 策略：后端接口未就绪时，使用 MSW（Mock Service Worker）或本地 mock 文件，mock 数据与后端契约保持一致。

联调环境：开发环境 API base URL 配置方式（.env.development / Vite proxy），避免跨域问题。

字段变更同步：后端接口字段调整时，前端类型定义和 mock 数据需同步更新，方案中可注明由谁负责同步及通知机制。
